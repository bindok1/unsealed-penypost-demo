# Backend Specification — Peny Post Creator Monetization & Shop Engine

## 0. Purpose

This document defines the desired backend behavior for the Peny Post creator shop and monetization system.

This is a specification, not an instruction to blindly introduce a new architecture.

### Mandatory AI Agent Protocol

Before creating migrations, models, handlers, services, routes, dependencies, or other code:

1. Scan the existing backend codebase first.
2. Identify the existing ORM/database layer.
3. Identify the existing router/framework and middleware pattern.
4. Identify the existing authentication and user identity system.
5. Identify the existing API response/error format.
6. Identify existing storage/upload infrastructure.
7. Identify existing RevenueCat integration, if any.
8. Identify existing naming conventions, primary-key conventions, migrations, and transaction patterns.
9. Identify reusable services/components before creating new ones.
10. Implement this specification using existing project conventions wherever possible.

Existing project architecture takes precedence for implementation details.
This document takes precedence for the new feature's required behavior and business rules.

---

# 1. System Scope

The backend is responsible for:

- Creator records and creator portal access
- Creator product/catalog management
- Product assets
- Shop showcase data
- User inventory
- One-time purchases
- RevenueCat webhook processing
- Creator royalty accounting
- Payout records
- Product views and likes
- Product publishing/review state
- APIs consumed by the mobile app and web admin

The system should support permanent digital ownership.

A successfully completed purchase unlocks the purchased item for the user without an expiration date.

Penypost does not expose a customer-facing refund feature.

Store-initiated purchase reversals/refunds must only be handled if the underlying app store / RevenueCat reports them.

# 2. Core Domain Model

## 2.1 creators

Represents creators who publish assets through Peny Post.

Suggested fields:

- id
- name
- email
- magic_token or equivalent secure portal credential
- payout_country
- payout_method
- payout_details
- unpaid_balance
- created_at
- updated_at

Do not introduce a new primary-key strategy if the existing project already has one.

Payout details must not be exposed in public/mobile APIs.

## 2.2 items

Represents a purchasable creator product/catalog item.

Suggested fields:

- id
- creator_id
- category
- tier
- title
- description
- sub_description
- thumbnail_url
- showcase_banner_url
- is_showcase_banner
- banner_order
- stamps_count
- stickers_count
- papers_count
- envelopes_count
- views_count
- likes_count
- sales_count
- publication_status
- created_at
- updated_at

Recommended publication states:

- DRAFT
- PENDING_REVIEW
- PUBLISHED
- REJECTED
- ARCHIVED

If the existing project convention requires a boolean such as is_published, preserve compatibility, but ensure the review workflow cannot become ambiguous.

## 2.3 item_assets

Represents individual assets included in an item.

Suggested fields:

- id
- item_id
- asset_type
- asset_url
- sort_order

Supported asset types:

- STAMP
- STICKER
- PAPER
- ENVELOPE

## 2.4 user_inventories

Represents permanent ownership of an item by a user.

Suggested fields:

- id
- user_id
- item_id
- unlocked_via
- unlocked_at

Supported unlock sources:

- IAP
- ENERGY
- REDEEM

Recommended unique constraint:

UNIQUE(user_id, item_id)

## 2.5 purchase_transactions

The backend must keep a durable purchase record for webhook idempotency and accounting.

Suggested fields:

- id
- user_id
- item_id
- tier
- revenuecat_event_id
- store_transaction_id
- gross_amount
- currency
- status
- created_at
- updated_at

Recommended purchase states:

- COMPLETED
- REVERSED

Repeated webhook delivery must never create duplicate inventory, duplicate sales, or duplicate creator earnings.

## 2.6 creator_earnings

Represents creator royalty generated by a purchase.

Suggested fields:

- id
- creator_id
- item_id
- user_id
- purchase_transaction_id
- tier
- royalty_amount
- currency
- status
- payout_id
- created_at
- paid_at

Supported statuses:

- UNPAID
- PAID
- REVERSED

## 2.7 payouts

Represents a completed creator payout.

Suggested fields:

- id
- creator_id
- amount
- currency
- receipt_url
- paid_at
- created_at

Payouts should be linked to the earning records that they settle.

## 2.8 item_likes

Stores per-user like state.

Suggested fields:

- id
- item_id
- user_id
- created_at

Required constraint:

UNIQUE(item_id, user_id)

# 4. Purchase Flow

```text
Mobile User
    ↓
Select Product
    ↓
RevenueCat Purchase
    ↓
Google Play / App Store
    ↓
RevenueCat Event
    ↓
Backend Webhook
    ↓
Validate Event
    ↓
Resolve Product + Tier
    ↓
Create Purchase Transaction
    ↓
Grant User Inventory
    ↓
Create Creator Earning
    ↓
Update Creator Balance
    ↓
Increment Sales
```

All accounting operations should be atomic according to the existing database architecture.

# 5. RevenueCat Webhook

## Endpoint

POST /api/v1/webhooks/revenuecat

The webhook must verify the configured webhook secret.

The backend should not trust a client callback as the source of truth for accounting.

The handler should:

1. Validate the webhook.
2. Identify the RevenueCat event.
3. Extract the authenticated app user ID.
4. Resolve the purchased product/package.
5. Resolve the Penypost item and tier through a trusted backend mapping.
6. Check whether the event/transaction has already been processed.
7. If already processed, return success without duplicating accounting.
8. Create the purchase transaction.
9. Grant inventory.
10. Create creator earning.
11. Update creator unpaid balance.
12. Increment item sales.
13. Commit.
14. Return HTTP 200.

---

# 6. Product / RevenueCat Mapping

The implementation must define a trusted mapping between:

- RevenueCat product/package
- Penypost tier
- Penypost item

The exact implementation should be selected after scanning the existing RevenueCat integration.

Do not create a second purchase configuration system if one already exists.

---

# 7. Purchase Reversal Handling

Penypost does not expose a customer-facing refund button.

Purchases are intended to be permanent.

If the store/RevenueCat reports that a completed purchase has been refunded, revoked, or otherwise reversed:

1. Locate the original purchase transaction.
2. Ensure the reversal is processed only once.
3. Mark the purchase as REVERSED.
4. Revoke the associated inventory according to the existing inventory model.
5. Create the required negative accounting adjustment if creator royalty has already been credited.
6. Update creator balance.
7. Record the reversal for auditability.

Do not invent a customer-facing refund workflow.

# 8. Shop APIs

## GET /api/v1/shop/showcase

Return published showcase items, sorted by banner order.

Suggested fields:

- id
- title
- sub_description
- description
- showcase_banner_url
- thumbnail_url
- tier
- category
- creator display name

## GET /api/v1/items

Catalog endpoint should support:

- category filtering
- pagination
- sorting
- product metadata
- creator display name
- asset composition counts
- tier/price information
- like count
- current user's like state when authenticated

Only published products are visible to normal mobile users.

## GET /api/v1/items/:id

Return product information, creator display information, previews, tier, price mapping, likes, current user's like state, and ownership state.

Do not expose private creator payout information.

---

# 9. User Inventory API

## GET /api/v1/me/inventory

Return permanently owned products and their assets.

The response must allow the mobile app to retrieve:

- owned products
- stamps
- stickers
- papers
- envelopes

This inventory is the bridge between the Shop and the Letter Composer.

---

# 10. Views

## POST /api/v1/items/:id/view

Called when a product detail page is meaningfully opened.

Requirements:

- only count valid published items
- avoid obvious request spam
- client-side debounce may be used
- backend should provide additional protection where practical
- view counting should not block the main product response

Use Redis only if it matches the existing infrastructure.

---

# 11. Likes

## POST /api/v1/items/:id/like

Toggle the authenticated user's like.

Expected behavior:

- no existing like → create and increment
- existing like → remove and decrement

The operation should be safe under concurrent requests.

# 12. Creator Portal

## GET /api/v1/creators/portal/:token

Return:

### Profile
- creator name
- creator email
- payout method status

### Financial
- unpaid balance
- payout currency
- minimum payout threshold
- payout eligibility

### Products
- title
- preview
- publication status
- views
- likes
- sales

Never return raw payout credentials unnecessarily.

---

# 13. Payout

Admin operations should support:

- list eligible creators
- inspect unpaid earnings
- create payout
- attach transfer receipt
- mark earnings as paid

Payout should settle specific earning records rather than simply resetting a numeric balance.

The system must prevent a payout from accidentally omitting earnings created concurrently.

Initial schedule:

- manual processing
- target period: 20th–25th each month
- previous sales period
- subject to store settlement timing

---

# 14. Asset Storage

The AI agent must first identify the project's existing object storage/upload architecture.

Do not introduce a new storage provider unless required.

Conceptual flow:

```text
Web Admin
    ↓
Upload / signed upload flow
    ↓
Object Storage
    ↓
Validate asset
    ↓
Store asset URL + metadata
    ↓
Attach asset to Item
```

Supported asset types:

- Stamp: transparent PNG/WebP
- Sticker: transparent PNG/WebP
- Paper: WebP/JPG
- Envelope: WebP/PNG
- Showcase banner: WebP

---

# 15. Admin Authorization

Admin-only operations must use the existing authentication and authorization system.

Creator routes must only expose authorized creator data.

Do not create a second authentication system if one already exists.

---

# 16. API Response Contract

Before implementation, inspect existing backend responses.

If a standard response envelope exists, reuse it.

If none exists, a possible structure is:

```json
{
  "success": true,
  "data": {},
  "message": "OK"
}
```

Errors should have stable machine-readable error codes where appropriate.

---

# 17. Transaction & Concurrency Requirements

The following must be safe against duplicate/concurrent processing:

- RevenueCat webhook processing
- inventory granting
- creator earning creation
- sales count increment
- payout settlement
- like toggling

Use the existing database transaction/locking conventions.

---

# 18. Auditability

The system should be able to answer:

- Which user purchased an item?
- Which item was purchased?
- Which creator owns it?
- Which RevenueCat/store transaction generated the earning?
- How much royalty was generated?
- Has it been paid?
- Which payout settled it?
- Was the purchase reversed?
